# Resource Calendars для Process Digital Twin

Resource Calendar расширяет стохастический Digital Twin рабочими сменами и плановой недоступностью ресурсов.

Используется в основном режиме:

```text
/?view=process-digital-twin
```

## 1. Рабочее окно

Для ресурса можно включить повторяющуюся 24-часовую смену, например:

```text
Оператор
08:00 → 17:00
```

Операция должна **полностью поместиться** внутри рабочего окна. Модель не дробит одну непрерывную операцию на две смены.

Пример:

```text
готовность операции: 16:30
длительность:        1:00
смена:               08:00–17:00
```

Запуск будет перенесён на `08:00` следующего дня.

Это соответствует non-preemptive модели: после старта операция выполняется непрерывно.

## 2. Плановый downtime

Downtime задаётся абсолютным временем от `t=0` симуляции.

Например:

```text
ТО стейнера:
start = 10 h
end   = 11 h
```

Если операция пересекает окно ТО, scheduler переносит её после завершения downtime и повторно проверяет рабочую смену.

## 3. Совместное требование нескольких ресурсов

Если блок требует одновременно, например:

```text
1 × оператор
1 × автомат
```

scheduler ищет первый интервал, в котором одновременно выполняются:

1. оба ресурса находятся в своих рабочих окнах;
2. оба ресурса не находятся в planned downtime;
3. на обоих ресурсах есть свободные capacity lanes;
4. вся длительность операции помещается в найденный интервал.

## 4. Utilization

Без календарей utilization обычно считается как:

```text
busy unit time / (makespan × capacity)
```

При включённом Resource Calendar знаменатель меняется:

```text
busy unit time / available unit time
```

где `available unit time` — сумма рабочих окон за горизонт симуляции минус planned downtime, умноженная на capacity ресурса.

Поэтому оператор, занятый 7 часов из доступных 9, получает utilization около `77.8%`, а не около `29%` от календарных суток.

Отдельно выводится `availabilityPercent` — доля календарного горизонта, когда ресурс вообще был доступен для работы.

## 5. Ограничения текущей версии

- UI описывает одно повторяющееся дневное окно на ресурс;
- overnight-смена вида `20:00–08:00` пока не задаётся одной строкой UI;
- planned downtime задаётся одним абсолютным окном из UI, хотя движок поддерживает массив окон;
- active task не прерывается отказом или окончанием смены: scheduler допускает старт только когда задача заранее полностью помещается в окно;
- случайные поломки MTBF/MTTR пока не моделируются.

## 6. Следующий уровень

Следующая логичная итерация цифрового двойника:

- stochastic equipment failures по MTBF;
- repair windows по MTTR;
- отдельные политики `fail-before-start` и `interrupt-active-task`;
- restart/resume после отказа;
- многосменные и недельные календари;
- праздники и исключения;
- unified stochastic batch scheduling для роторов/racks/stainers.

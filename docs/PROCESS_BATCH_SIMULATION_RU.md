# Batch-Cycle Process Simulation

Этот режим расширяет обычную ресурсную симуляцию для оборудования, которое обрабатывает несколько образцов **одним общим технологическим циклом**.

Типичные примеры:

- центрифуга с ротором/корзиной;
- автоматический stainer с rack;
- инкубационная станция;
- мойка/окраска кассетой;
- термоцикл или иной общий цикл для группы образцов.

## Запуск

```text
http://localhost:3000/?view=process-batch
```

или:

```text
http://localhost:3000/#process-batch
```

Режим читает последнюю сохранённую модель `Process Simulation` и поверх неё добавляет batch-политику для выбранных блоков.

## Почему обычной capacity недостаточно

В обычной resource simulation:

```text
resource capacity = число независимых параллельных единиц обслуживания
```

Например, две одинаковые центрифуги — это `capacity = 2`.

Но ротор на 12 проб — не `capacity = 12` в этом смысле. Это один ресурс, который запускает **один общий цикл** на несколько проб.

Поэтому batch-модель разделяет:

```text
resource.capacity   = число одновременно доступных аппаратов/станций
batchCapacity       = число образцов внутри одного цикла
```

Пример:

```text
Центрифуга: resource.capacity = 1
Ротор:      batchCapacity = 12
```

Один 8-минутный запуск центрифуги занимает ресурс один раз и одновременно завершает до 12 образцов.

## Параметры batch-блока

### Batch capacity

Максимальное число образцов в одном общем цикле.

### Min batch size

Минимальное число готовых образцов, которое желательно накопить до запуска цикла.

### Max wait

Максимальное время ожидания самой ранней готовой пробы.

Если `minBatchSize` ещё не набран, но первая проба ждёт дольше `maxWaitSeconds`, разрешается запустить неполную партию.

Таким образом можно моделировать компромисс:

```text
эффективность заполнения оборудования ↔ turnaround time отдельного образца
```

## Алгоритм

Для каждого batch-блока:

1. собираются образцы, у которых завершены все DAG-предшественники;
2. определяется `ready time` каждого образца;
3. вычисляется момент, когда:
   - набран `minBatchSize`, либо
   - истёк `maxWaitSeconds` для первой готовой пробы;
4. выбирается до `batchCapacity` готовых образцов;
5. ищется самый ранний общий интервал доступности всех ресурсов блока;
6. ресурсы резервируются **один раз на batch cycle**;
7. всем образцам внутри цикла присваиваются одинаковые `start` и `finish`;
8. индивидуальное ожидание каждого образца считается от его собственного `ready time`.

Если ресурсная занятость задерживает запуск, scheduler может дозаполнить batch дополнительными образцами, которые успели стать готовыми к фактическому старту.

## Метрики

### Average batch fill

```text
fill = samples_in_cycle / batchCapacity
```

Показывается среднее заполнение всех batch cycles.

### Partial cycles

Количество циклов, запущенных не полностью заполненными.

### Average batch size

Среднее число образцов в одном цикле конкретного batch-блока.

### Batch wait

Для каждого образца:

```text
wait = batch_start - sample_ready
```

Показываются среднее и максимальное ожидание.

### Makespan / throughput

Считаются уже с учётом batch-политики и общего использования ресурсов.

## Пример

Пусть:

```text
batchSize = 13 проб
центрифуга = 1 аппарат
batchCapacity = 12
minBatchSize = 12
cycleTime = 8 мин
```

При одновременной готовности всех проб scheduler сформирует:

```text
Cycle 1: 12 / 12 → 8 мин
Cycle 2:  1 / 12 → ещё 8 мин
```

Среднее заполнение двух циклов:

```text
(100% + 8.33%) / 2 ≈ 54.17%
```

Это принципиально отличается от модели, где 13 проб ошибочно считались бы 13 независимыми 8-минутными операциями.

## Применение к LBC

Для LBC этот режим особенно полезен для стадий, где реальное оборудование работает rack/rotor/batch-циклами.

При этом batch capacity, минимальный размер запуска и организационная политика ожидания должны вводиться из:

- IFU/официальной документации конкретной конфигурации;
- фактической лабораторной SOP;
- валидированных локальных наблюдений.

Модель не предназначена для самостоятельного изменения клинически валидированных параметров медицинского изделия или реагентного протокола.

## Следующие расширения

Следующий уровень модели может добавить:

- фиксированные времена плановых запусков rack;
- несколько batch-машин с разными корзинами;
- setup/changeover между типами партий;
- приоритет STAT/urgent;
- совместимость образцов внутри batch;
- балансировку ротора/парные позиции;
- сменные календари персонала;
- rework и QC reject;
- Monte Carlo поверх batch scheduling.

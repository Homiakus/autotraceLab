# Техническое задание

## Система построения функциональных блоков, портов, размещения и автоматической трассировки AutoTrace

**Версия:** 1.0
**Статус:** целевая спецификация архитектуры
**Область:** Block Model → Port Model → Block Geometry → Placement → Routing → Cleanup → Labels → Validation

---

# 1. Цель

Необходимо реализовать единую систему построения структурных, функциональных, электрических и логических схем, в которой каждый блок:

* имеет однозначную геометрию;
* имеет формально определённые порты;
* одинаково интерпретируется UI, TypeScript-движком и Go-движком;
* корректно участвует в автоматическом размещении;
* является препятствием для трассировщика;
* обеспечивает строго ортогональный выход соединений;
* поддерживает автоматическое изменение размеров;
* поддерживает фиксированные и адаптивные порты;
* сохраняет визуальную читаемость независимо от количества портов;
* не допускает наложения текста, портов и трасс;
* детерминированно строится из одних и тех же входных данных.

Главный принцип:

> **Семантика блока → геометрия блока → геометрия портов → topology graph → placement → routing → cleanup → labels → validation.**

Нельзя выполнять эти операции в произвольном порядке.

---

# 2. Проблемы текущей реализации, которые ТЗ должно устранить

В существующем проекте уже реализованы:

* `BlockNode`;
* `Port`;
* `EdgeConnection`;
* формы `rectangle`, `rounded`, `chip_ic`, `circle`, `diamond`, `hexagon`;
* четыре стороны размещения портов;
* `fixed/adaptive`;
* `relativePosition`;
* A* ортогональная трассировка;
* Sugiyama;
* barycentric ordering;
* pin alignment;
* очистка jog/staircase;
* label layout;
* joint co-optimization.

Однако модель пока не полностью едина.

### 2.1. Разные представления в TypeScript и Go

TypeScript-порт содержит:

```text
placementMode
relativePosition
customOffset
pinNumber
dataType
color
description
```

Go-порт фактически содержит только:

```text
ID
Name
Side
Type
OffsetPct
```

Это недопустимо.

После переноса вычислений в Go положение блока и порта может измениться относительно UI.

### 2.2. Геометрия фигур и геометрия портов расходятся

Сейчас `diamond` и `hexagon` визуально имеют непрямоугольный контур, но порт вычисляется относительно прямоугольного `width × height`.

Следовательно, порт визуально может оказаться:

* вне реального контура;
* внутри фигуры;
* на неправильной грани;
* с неправильной нормалью.

### 2.3. `circle` объявлен, но отсутствует полноценная отдельная реализация геометрии.

### 2.4. Размер блока задаётся практически вручную

Не учитывается полноценно:

* число портов;
* длина названий портов;
* длина заголовка;
* subtitle;
* изображение;
* минимальный pitch между портами.

### 2.5. Новый блок получает случайные `x/y`

Для production-системы:

```text
x = random(...)
y = random(...)
```

запрещено.

Начальная позиция должна определяться layout engine либо детерминированным свободным слотом.

# 3. Базовая архитектурная модель

Блок должен рассматриваться одновременно в трёх представлениях.

## 3.1. Semantic Model

Определяет, **что означает блок**:

```text
Block
 ├─ id
 ├─ title
 ├─ subtitle
 ├─ category
 ├─ semanticType
 ├─ inputs[]
 ├─ outputs[]
 ├─ metadata
 └─ constraints
```

---

## 3.2. Visual Model

Определяет, **как блок выглядит**:

```text
Visual
 ├─ shape
 ├─ color
 ├─ icon
 ├─ image
 ├─ header
 ├─ body
 ├─ border
 └─ selection state
```

---

## 3.3. Routing Model

Определяет, **как алгоритмы взаимодействуют с блоком**:

```text
RoutingGeometry
 ├─ routingBounds
 ├─ obstacleBounds
 ├─ portAnchors[]
 ├─ portNormals[]
 ├─ keepOutZone
 └─ preferredChannels
```

Это разделение принципиально важно.

Визуальная фигура не должна непосредственно определять поведение A*.

---

# 4. Routing Envelope

Каждый блок обязан иметь прямоугольный **routing envelope**.

```text
        keep-out zone
 ┌──────────────────────────────┐
 │                              │
 │    ┌────────────────────┐    │
 │ ●──┤                    ├──● │
 │    │    VISUAL BLOCK    │    │
 │ ●──┤                    ├──● │
 │    └────────────────────┘    │
 │                              │
 └──────────────────────────────┘
```

Routing envelope определяет:

* координаты подключения;
* положение портов;
* нормали;
* obstacle avoidance;
* минимальный clearance.

Таким образом, даже:

* diamond;
* circle;
* hexagon;
* произвольное SVG;
* изображение устройства

могут участвовать в одном ортогональном routing engine.

# 5. Анатомия стандартного блока

Стандартный функциональный блок:

```text
       ┌────────── TOP PORTS ──────────┐
       │      ●        ●        ●      │
       ▼                               ▼
    ┌─────────────────────────────────────┐
 ●──┤ ● BLOCK NAME             PROCESSOR │──●
 ●──┤─────────────────────────────────────│──●
 ●──┤                                     │──●
    │             CONTENT                 │
 ●──┤                                     │──●
    │                                     │
    │ subtitle / model                    │
    └─────────────────────────────────────┘
       ▲                               ▲
       │      ●        ●        ●      │
       └──────── BOTTOM PORTS ─────────┘
```

Блок состоит из:

1. внешнего контура;
2. заголовка;
3. category indicator;
4. основной области;
5. optional image/icon;
6. subtitle;
7. портов;
8. port labels;
9. connection anchors;
10. selection outline;
11. pin/freeze indicator.

# 6. Сетка

Все геометрические размеры должны быть основаны на общей базовой сетке.

Рекомендуется:

```text
baseGrid = 4 px
placementGrid = 10 px
routingGrid = 10 px
```

Физические размеры компонентов UI кратны `2/4 px`.

Координаты блоков при автоматическом placement должны быть кратны `placementGrid`.

---

# 7. Стандартные размеры блока

Исходный размер существующей реализации:

```text
180 × 110 px
```

может быть сохранён как `default`.

Целевые значения:

```text
defaultWidth  = 180
defaultHeight = 110

minWidth  = 120
minHeight = 72

headerHeight = 24
bodyPadding  = 12
cornerRadius = 12
```

Жёсткий `maxWidth/maxHeight` на уровне модели вводить не требуется.

UI может рекомендовать:

```text
manual width: 120–480 px
manual height: 72–400 px
```

---

# 8. Автоматический расчёт размеров

Размер блока должен вычисляться **до placement**.

Для каждой стороны вычисляется количество портов:

```text
NL
NR
NT
NB
```

Определяется:

```text
Nvertical   = max(NL, NR)
Nhorizontal = max(NT, NB)
```

Минимальный pitch:

```text
portPitch = 20 px
```

Безопасная зона около углов:

```text
cornerPortMargin >= 14 px
```

Тогда:

```text
Hports =
    2 × cornerPortMargin
    + max(0, Nvertical - 1) × portPitch
```

и:

```text
Wports =
    2 × cornerPortMargin
    + max(0, Nhorizontal - 1) × portPitch
```

Отдельно рассчитывается размер содержимого.

```text
Wtitle
Wsubtitle
Wimage
WleftLabels
WrightLabels
```

Финальная ширина:

```text
W =
snap(
    max(
        minWidth,
        Wtitle + headerControls + padding,
        Wports,
        Wcontent
    ),
    grid
)
```

Финальная высота:

```text
H =
snap(
    max(
        minHeight,
        headerHeight + bodyHeight + padding,
        Hports
    ),
    grid
)
```

---

# 9. Нельзя сжимать блок ниже размера, необходимого портам

Например, на правой стороне 8 портов.

При:

```text
margin = 14
pitch  = 20
```

получаем:

```text
Hmin = 14×2 + 7×20
     = 168 px
```

Следовательно, пользователь не может уменьшить блок до 100 px высоты.

UI должен показать:

> Минимальная высота блока при текущей конфигурации портов: 168 px.

# 10. Формы блоков

Поддерживаются следующие типы.

## rectangle

Использование:

* абстрактные функциональные модули;
* сервисы;
* устройства.

Контур строго прямоугольный.

---

## rounded

Основной универсальный тип.

```text
radius = 12 px
```

Рекомендуется использовать по умолчанию.

---

## chip_ic

Для:

* MCU;
* FPGA;
* SoC;
* IC;
* контроллеров.

Особенности:

* IC notch;
* Pin-1 marker;
* преимущественно фиксированные порты;
* поддержка pin numbers.

---

## circle

Используется только для семантически оправданных сущностей:

* junction;
* clock;
* external connector;
* special process.

Для настоящего круга:

```text
width == height
```

При различающихся размерах используется `ellipse`, который должен быть отдельным типом.

---

## diamond

Используется для:

* decision;
* condition;
* branch;
* comparator.

По умолчанию допускается максимум один основной порт на каждое направление:

```text
LEFT
RIGHT
TOP
BOTTOM
```

Если требуется большое количество портов, автоматически применять `routingFrame`.

---

## hexagon

Используется для специальных вычислительных или преобразующих модулей.

Рекомендуется сохранять прямоугольный routing envelope независимо от визуального контура.

---

# 11. Принцип Visual Shape ≠ Routing Shape

Это одно из главных правил системы.

Например:

```text
Routing Envelope

┌───────────────────────┐
│          ●            │
│        /   \          │
●────── / HEX \ ────────●
│      \       /        │
│        \___/          │
│          ●            │
└───────────────────────┘
```

A* считает препятствием прямоугольный envelope.

Пользователь видит hexagon.

Это устраняет сложности:

* определения нормали наклонной поверхности;
* диагонального выхода;
* нарушения Manhattan topology.

# 12. Модель порта

Каждый порт должен иметь единый контракт:

```text
Port {
    id
    name
    direction
    dataType

    side
    placementMode

    relativePosition
    customOffset

    pinNumber

    preferredSide
    allowedSides[]

    order
    groupId

    color
    description

    minSpacing
}
```

---

# 13. Direction порта

Допустимые значения:

```text
input
output
inout
passive
```

Необходимо добавить `inout`, так как оно требуется для:

* I²C SDA;
* GPIO;
* CAN;
* bidirectional buses;
* аналоговых линий.

---

# 14. Data Type

Минимальный набор:

```text
signal
bus
clock
power
control
trigger
data
analog
ground
network
mechanical
custom
```

`dataType` определяет:

* цвет;
* допустимость подключения;
* толщину линии;
* routing priority;
* поведение группировки.

---

# 15. Цветовая семантика портов

Текущая схема может быть сохранена как базовая:

```text
signal input   #3b82f6
signal output  #38bdf8

bus            #8b5cf6
clock          #10b981
power          #f59e0b
control        #f43f5e
```

Цвет является secondary indicator.

Нельзя использовать только цвет для передачи смысла.

---

# 16. Стороны порта

```text
left
right
top
bottom
```

По умолчанию:

```text
input   → left
output  → right
```

Рекомендуемая семантика:

```text
LEFT    входной поток
RIGHT   выходной поток
TOP     питание / clock / upstream service
BOTTOM  reset / control / feedback / service
```

Однако пользователь имеет право переопределить сторону.

---

# 17. Fixed Port

`fixed` означает:

> положение порта является частью контракта компонента.

Пример:

```text
STM32 Pin 1
VDD
GND
NRST
physical connector
```

Для fixed-порта задаётся:

```text
side
relativePosition
```

где:

```text
0.0 <= relativePosition <= 1.0
```

Практический UI-range:

```text
0.05–0.95
```

Но фактическое положение дополнительно ограничивается `cornerPortMargin`.

---

# 18. Adaptive Port

Adaptive означает:

> алгоритм имеет право автоматически выбирать оптимальное положение порта.

Есть два уровня адаптивности.

### adaptive_distribute

Сторона фиксирована, координата меняется.

Например:

```text
side = left
```

но `y` выбирается автоматически.

### adaptive_faces

Алгоритм может выбрать:

```text
left/right/top/bottom
```

из `allowedSides`.

Это необходимо реализовать отдельно.

Существующее поле:

```text
portsAdaptiveMode
```

следует заменить формализованной политикой.

---

# 19. Распределение adaptive-портов

Для `N` портов на одной стороне:

```text
t_i = (i + 1)/(N + 1)
```

где:

```text
i = 0 ... N-1
```

Тогда:

```text
LEFT:
x = X
y = Y + clamp(t_i × H)

RIGHT:
x = X + W
y = Y + clamp(t_i × H)

TOP:
x = X + clamp(t_i × W)
y = Y

BOTTOM:
x = X + clamp(t_i × W)
y = Y + H
```

После этого выполняется collision-aware refinement.

---

# 20. Port ordering

Порядок портов нельзя определять только порядком массива.

Вводится:

```text
order: integer
```

Сначала сортировка:

```text
group
→ priority
→ order
→ stable ID
```

Это гарантирует детерминированность схемы.

---

# 21. Port Groups

Порты должны поддерживать группы.

Например:

```text
SPI
 ├─ SCK
 ├─ MOSI
 ├─ MISO
 └─ CS

I2C
 ├─ SDA
 └─ SCL
```

Группа должна по возможности занимать соседние позиции.

Нельзя размещать:

```text
SCK
ADC
MOSI
RESET
MISO
```

если они относятся к одной шине.

Fixed:

```text
□
```

Квадратный pad.

Размер:

```text
9 × 9 px
```

Hover:


Adaptive:


# 23. Нормаль порта

У каждого порта рассчитывается нормаль.

```text
LEFT   (-1, 0)
RIGHT  (+1, 0)
TOP    (0, -1)
BOTTOM (0, +1)
```

Она является жёстким геометрическим инвариантом трассировки.

---

# 24. Главное правило подключения

Первый участок линии обязан совпадать с нормалью source-порта.

Последний участок линии обязан совпадать с обратной нормалью target-порта.

То есть линия всегда входит в блок под:

```text
90°
```

и никогда:

```text
↗
↘
↖
↙
```

---

# 25. Port Exit Stub

Перед началом свободной трассировки создаётся обязательный stub:

```text
P_stub = P_port + normal × L_stub
```

Базовое значение:

```text
L_stub = 20 px
```

Допустимый диапазон:

```text
16–40 px
```

---

# 26. Adaptive Stub

Stub должен зависеть от свободного пространства.

Если расстояние между блоками мало:

```text
L_stub <= distance / 2 - safetyGap
```

Если перед портом находится препятствие:

```text
L_stub <= obstacleDistance / 2 - safetyGap
```

Если несколько трасс выходят с одной грани, используется stagger:

```text
L_i =
L_base
+ (i - (N-1)/2) × Δ
```

где:

```text
Δ ≈ 6 px
```

Этот механизм уже частично присутствует в проекте и должен быть оформлен как обязательное правило.

# 27. Алгоритм создания одного блока

## Этап B1 — Normalization

Получить исходное описание:

```text
title
category
shape
ports
image
metadata
constraints
```

Проверить обязательные значения.

---

## B2 — Semantic validation

Проверить:

```text
unique block ID
unique port ID inside block
valid directions
valid sides
valid dataType
valid groups
```

---

## B3 — Port classification

Разделить:

```text
portsLeft
portsRight
portsTop
portsBottom
```

Затем внутри каждой стороны:

```text
fixed
adaptive
```

---

## B4 — Fixed anchor reservation

Сначала располагаются fixed-порты.

Их позиции объявляются занятыми интервалами:

```text
[position - minSpacing,
 position + minSpacing]
```

---

## B5 — Adaptive free-space calculation

Свободная длина стороны:

```text
FreeSegments =
SideLength
- CornerMargins
- FixedPortIntervals
```

---

## B6 — Adaptive distribution

Adaptive-порты распределяются по свободным сегментам таким образом, чтобы минимизировать:

```text
Σ deviationFromUniform
+ Σ groupSplitPenalty
+ Σ crossingPrediction
```

---

## B7 — Auto Size

Проверяется, хватает ли текущей длины сторон.

Если нет:

```text
width++
или
height++
```

до выполнения:

```text
distance(port_i, port_j) >= minPortPitch
```

---

## B8 — Build routing envelope

Создаются:

```text
routingBounds
obstacleBounds
keepOutBounds
```

---

## B9 — Build visual geometry

Отдельно строится:

```text
rectangle
rounded rectangle
IC
circle
diamond
hexagon
```

---

## B10 — Text layout

Размещаются:

```text
header
title
category
subtitle
port labels
```

---

## B11 — Collision validation

Проверяются:

```text
port ↔ port
port label ↔ port label
title ↔ controls
title ↔ category
subtitle ↔ port labels
```

---

## B12 — Finalization

После успешной валидации блок получает статус:

```text
geometryState = valid
```

Только после этого он может передаваться placement engine.

---

# 30. Этап 1 — Graph normalization

Убираются ошибки:

* connection to nonexistent port;

# 31. Этап 2 — Определение основного направления

По умолчанию:

```text
LEFT → RIGHT
```

Источники должны стремиться к левому краю.

Приёмники — к правому.

Feedback-связи допускаются, но не должны ломать основной flow.

---

# 32. Этап 3 — Cycle detection

DFS определяет feedback edges.

Циклические связи временно исключаются при построении DAG.

Важно:

> Логическое направление Edge не изменяется.

Создаётся только временное представление:

```text
layoutEdgeDirection
```

---

# 33. Этап 4 — Layer Assignment

Использовать modified longest-path / network-simplex layering.

Получить:

```text
L0
L1
L2
...
Ln
```

Например:

```text
Sensors → Processing → Decision → Actuator
```

---

# 34. Этап 5 — Dummy Nodes

Связь, пересекающая несколько слоёв:

```text
L0 → L3
```

должна внутренне преобразовываться:

```text
L0 → D1 → D2 → L3
```

Dummy nodes не отображаются.

Они необходимы для корректного Sugiyama ordering.

---

# 35. Этап 6 — Crossing Reduction

Использовать:

* barycenter;
* median;
* transpose/local swap.

Порядок блока оценивается не только по центрам соседей, но и по **координатам портов**.

Целевая функция:

```text
Ccross =
numberOfEdgeCrossings
+ λ × portOrderingConflicts
```

---

# 36. Этап 7 — Расчёт ширины межслойного канала

Ширина пространства между слоями зависит от количества соединений.

Пример:

```text
ChannelWidth =
baseChannel
+ trackCount × trackPitch
```

Рекомендуется:

```text
baseChannel = 80–120 px
trackPitch  = 14–20 px
```

Не следует всегда использовать фиксированные 160 px.

---

# 37. Этап 8 — X Coordinate Assignment

Для слоя:

```text
X[L+1] =
X[L]
+ maxWidth[L]
+ channelWidth[L]
```

Таким образом блоки одного слоя находятся на одной logical X-column.

---

# 38. Этап 9 — Y Coordinate Assignment

Внутри слоя блоки первоначально располагаются с:

```text
nodeGap >= 40 px
```

Затем начинается pin-aware optimization.

---

# 39. Этап 10 — Pin Alignment

Если блок A соединён с B:

```text
A.out.y ≈ B.in.y
```

то связь может стать:

```text
─────────────>
```

без единого поворота.

Целевая функция:

```text
Calign =
Σ |YsourcePort - YtargetPort|
```

Но alignment не может нарушать:

```text
block clearance
node order
pinned nodes
```

---

# 40. Приоритет прямых линий

Если два соседних блока имеют facing ports:

```text
RIGHT → LEFT
```

и:

```text
|Ys - Yt| <= tolerance
```

и свободный corridor существует,

маршрут должен быть:

```text
[Psource, Ptarget]
```

То есть:

```text
bendCount = 0
```

A* в этом случае запускать не требуется.

---

# 41. Этап 11 — Vertical collision resolver

После pin snapping возможно пересечение блоков.

Для каждой пары одного слоя должно выполняться:

```text
Ynext >=
Ycurrent
+ Hcurrent
+ NodeGap
```

При конфликте сначала сдвигается блок с меньшим:

```text
alignmentPriority
```

Pinned block не перемещается никогда.

---

# 42. Этап 12 — Routing obstacles

Для блока:

```text
Obstacle =
routingBounds
expanded by obstacleClearance
```

Типовое:

```text
obstacleClearance = 16 px
```

---

# 43. Этап 13 — Routing grid

A* работает по Manhattan grid.

```text
gridSize = 10 px
```

Состояние должно содержать:

```text
x
y
incomingDirection
```

а не только `x/y`.

Это необходимо для корректного штрафа за bend.

---

# 44. A* Cost Function

Стоимость шага:

```text
G =
wireLengthCost
+ bendPenalty
+ congestionPenalty
+ proximityPenalty
+ crossingPenalty
- straightContinuationBonus
- targetAlignmentBonus
```

---

# 45. Bend penalty

Поворот на 90° должен быть значительно дороже обычного шага.

Например:

```text
step       = 10
bend       = 30–50
```

Это заставляет A* выбирать:

```text
────────────
           │
```

вместо многочисленных ступеней.

---

# 46. Запрет коллинеарного наложения

Две независимые линии не имеют права использовать один и тот же сегмент:

```text
════════════
════════════
```

Если сегмент занят:

```text
cost = ∞
```

Исключение допускается только для специально определённых:

```text
bus trunk
shared net
junction
```

---

# 47. Перпендикулярные пересечения

Допускаются:

```text
──────┼──────
      │
      │
```

Но визуально должны различаться:

* bridge;
* hop;
* junction.

---

# 48. Junction semantics

Если электрическое соединение существует:

```text
──────●──────
      │
```

Если соединения нет:

```text
──────∩──────
      │
```

Нельзя определять это только визуально.

У Edge/Junction должна присутствовать семантика.

---

# 49. Congestion Map

После прокладки каждой трассы обновляется поле занятости.

Для каждой routing-cell:

```text
usage[x,y]
proximity[x,y]
```

Соседние клетки получают penalty.

Это создаёт естественный spacing между параллельными проводниками.

---

# 50. Недостаток последовательного A*

Последовательная прокладка:

```text
route E1
route E2
route E3
...
```

зависит от порядка рёбер.

Поэтому production-алгоритм должен выполнять минимум несколько проходов.

---

# 51. Negotiated Congestion Routing

Рекомендуемый алгоритм:

```text
Pass 1:
    route all nets

Measure congestion

Rip-up conflicting nets

Increase history cost

Pass 2:
    reroute conflicts

Repeat
```

Стоимость ресурса:

```text
cost =
baseCost
+ presentCongestion
+ historyCongestion
```

Рекомендуется 3–10 итераций.

---

# 52. Приоритет порядка трассировки

Маршруты сортируются по:

```text
1 critical/pinned nets
2 clocks
3 buses
4 power
5 control
6 signals
```

Затем по сложности:

```text
fewer feasible corridors first
```

а не исключительно по минимальной Manhattan distance.

# 60. Скругление углов

Вычислительная модель пути остаётся ортогональной.

То есть:

```text

```

хранится в topology.

Только renderer может заменять угол на:

```text
line + arc + line
```

# 61. Adaptive Corner Radius

Для сегментов длиной:

```text
L1
L2
```

радиус:

```text
r =
min(
    userRadius,
    0.4 × L1,
    0.4 × L2
)
```

Таким образом короткие участки не ломаются.

# 62. Label Placement

Сначала строится wire.

Только потом label.

---

# 63. Label должен находиться на собственной линии

Основной инвариант:

```text
label.isOnArrow == true
```

При наличии возможности запрещено размещать label отдельно от провода.

---

# 64. Выбор участка для label

Для каждого сегмента вычисляется:

```text
score =
segmentLength
- obstaclePenalty
- labelCollisionPenalty
- crossingPenalty
- endpointPenalty
```

Выбирается сегмент с максимальным score.

# 65. Минимальная длина сегмента

Если ширина текста:

```text

```

то:

```text
Lsegment >= Wlabel + 2 × labelPadding
```

Иначе сегмент не является кандидатом.

# 66. Label collision relaxation

```text
label ↔ other label
```

# 81. Алгоритм при добавлении нового блока

Не использовать random coordinate.

Порядок:

```text

2 determine probable layer
3 find free slot
4 create provisional position
5 local crossing reduction
6 local compaction
7 reroute affected edges
```

Если связей ещё нет:

```text
find nearest empty slot
```

по deterministic spiral/grid search.

```text
↓

↓

↓

↓

↓

↓

↓
```

Не обязательно каждый раз перестраивать всю схему.

# 102. Канонический алгоритм построения блока

В окончательной форме:

```text
function BuildBlock(spec):

    Normalize(spec)

    ValidateSemanticModel(spec)

    ports =
        NormalizePorts(spec.ports)

    fixed =
        ReserveFixedPorts(ports)

    adaptive =
        ClassifyAdaptivePorts(ports)

    size =
        CalculateMinimumBlockSize(
            title,
            subtitle,
            content,
            fixed,
            adaptive
        )

    routingBounds =
        BuildRoutingBounds(size)

    portAnchors =
        PlaceFixedPorts(
            routingBounds,
            fixed
        )

    freeIntervals =
        CalculateFreePortIntervals(
            routingBounds,
            portAnchors
        )

    portAnchors +=
        PlaceAdaptivePorts(
            adaptive,
            freeIntervals
        )

    visualGeometry =
        BuildVisualShape(
            shape,
            routingBounds
        )

    textLayout =
        LayoutText(
            title,
            subtitle,
            portLabels
        )

    violations =
        ValidateBlockGeometry(
            visualGeometry,
            routingBounds,
            portAnchors,
            textLayout
        )

    if violations affect size:
        resize
        repeat geometry pass

    return DerivedBlockGeometry
```

---

# 103. Канонический алгоритм построения схемы

```text
function BuildDiagram(model):

    NormalizeModel()

    ValidateConnections()

    for block:
        BuildBlock(block)

    graph =
        BuildTopology()

    layoutGraph =
        BreakCyclesForLayout(graph)

    layers =
        AssignLayers(layoutGraph)

    InsertDummyNodes()

    ReduceCrossings(
        layers,
        portAware = true
    )

    AssignInitialCoordinates()

    AlignConnectedPorts()

    ResolveBlockCollisions()

    CompactLayout()

    channels =
        BuildRoutingChannels()

    routes =
        RouteDirectConnectionsFirst()

    routes +=
        RouteRemainingNetsAStar()

    for iteration:
        DetectCongestion()
        RipUpConflicts()
        RenegotiateChannels()
        Reroute()

    for route:
        RemoveCollinearPoints()
        RemoveMicroJogs()
        RemoveUTurns()
        RemoveStaircases()

    PlaceLabels()

    BuildCrossingBridges()

    ValidateHardConstraints()

    CalculateMetrics()

    return Scene
```

# 104. Что считать хорошим визуальным результатом

Схема должна восприниматься как спроектированная инженером, а не автоматически сгенерированный граф.

Хорошая схема характеризуется:

```text
ровными колонками блоков
+
понятным потоком слева направо
+
соосными портами
+
длинными прямыми участками
+
небольшим числом изгибов
+
равномерными routing channels
+
отсутствием наложений
+
предсказуемым расположением подписей
```

Предпочтительно:

```text
──────────────>
```

Допустимо:

```text
───────┐
       │
       └────────>
```

Нежелательно:

```text
──┐
  └─┐
    └──┐
       └─>
```

Недопустимо:

```text
wire through block
overlapping wires
port on wrong contour
diagonal entry into port
labels over blocks
```

# 105. Итоговое ключевое правило

**Блок является атомарной единицей схемы.**

До начала глобального layout для каждого блока уже должны быть однозначно известны:

```text
size
routing bounds
obstacle bounds
ports
anchors
normals
labels
constraints
```

Layout имеет право менять:

```text
block.x
block.y
```

и, если явно разрешено:

```text
adaptive port position
```

но не имеет права самовольно менять семантику блока.

Routing не имеет права изменять placement.

Renderer не имеет права исправлять routing.

Таким образом получается строго разделённый pipeline:

**Model → Block Geometry → Placement → Routing → Cleanup → Labels → Validation → Render.**

Именно эту модель следует считать базовым контрактом для дальнейшего развития AutoTrace.

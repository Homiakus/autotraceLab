Для вашей задачи я бы выбрал архитектуру **Headless Go Core + WASM Runtime + TypeScript Presentation Layer**. То есть вся математика AutoTrace живёт в Go, а сайт и Obsidian отвечают только за ввод, взаимодействие и визуализацию.

```text
                    ┌───────────────────────────┐
                    │       Canonical Model     │
                    │ Blocks / Ports / Edges    │
                    └─────────────┬─────────────┘
                                  │
                     ┌────────────▼────────────┐
                     │     AUTOTRACE CORE      │
                     │          Go             │
                     │                         │
                     │ geometry                │
                     │ layout                  │
                     │ routing                 │
                     │ optimization            │
                     │ labels                  │
                     │ validation              │
                     │ metrics                 │
                     └───────┬────────┬────────┘
                             │        │
                    Native Go│        │WASM
                             │        │
                ┌────────────▼─┐   ┌──▼─────────────┐
                │ Server / CLI │   │ Browser Worker │
                │ Backend      │   │ WASM runtime   │
                └──────────────┘   └──────┬─────────┘
                                         │
                         ┌───────────────┴───────────────┐
                         │                               │
                  ┌──────▼──────┐                ┌───────▼──────┐
                  │ Web App     │                │ Obsidian     │
                  │ TypeScript  │                │ Plugin TS    │
                  └──────┬──────┘                └───────┬──────┘
                         │                               │
                         └───────────────┬───────────────┘
                                         │
                               ┌─────────▼─────────┐
                               │ Scene Renderer    │
                               │ Canvas/WebGL/SVG  │
                               └───────────────────┘
```

### Что я считаю лучшим вариантом

**Не делайте Go → HTTP → Obsidian как основной путь.** Это сразу создаст зависимость от локального сервера или интернета.

**Не пишите layout дважды: Go + TypeScript.** Иначе через несколько месяцев получите разные координаты блоков, портов и трасс.

**Не заставляйте Go управлять DOM/SVG.** Это сильно связывает математическое ядро с конкретным UI.

Нужно сделать один Go engine:

```text
input model
   ↓
Go Core
   ↓
immutable Scene
   ↓
TypeScript Renderer
```

Это позволяет использовать абсолютно один алгоритм на сайте, в Obsidian, CLI, backend и в будущем в desktop-приложении.

## 1. Go должен владеть всей геометрией

Я бы перенёс в Go абсолютно всё, что влияет на результат схемы:

```text
core/
├── model/
├── geometry/
├── ports/
├── graph/
├── layout/
├── optimize/
├── routing/
├── cleanup/
├── labels/
├── spatial/
├── metrics/
└── scene/
```

Например:

```go
type Engine interface {
    Build(Model, Options) (*Scene, error)
    Update(*Scene, Mutation, Options) (*ScenePatch, error)
}
```

UI не должен рассчитывать даже:

```text
port.x
port.y
stub
block bounds
edge path
label position
```

В TypeScript он получает уже:

```ts
scene.blocks[i].geometry
scene.ports[i].x
scene.ports[i].y
scene.edges[i].segments
scene.labels[i].bounds
```

и только рисует.

---

# 2. Один Go-код → два target

Это самое важное решение.

Нативная сборка:

```bash
go build ./cmd/autotrace
```

и browser:

```bash
GOOS=js GOARCH=wasm go build -o autotrace.wasm ./cmd/wasm
```

Официальный Go поддерживает `js/wasm`, а WebAssembly можно исполнять как в браузере, так и через Node.js. Начиная с Go 1.24 появился `//go:wasmexport`, что существенно улучшило возможность построения нормального ABI между Go/Wasm и хостом. ([Go][1])

Поэтому сейчас я бы **сначала использовал обычный Go compiler, а не TinyGo**.

---

# 3. Почему я не рекомендую сразу TinyGo

TinyGo сейчас вполне зрелый для WASM и в актуальной документации поддерживает прямой экспорт функций; есть также оптимизация `-opt=2` для скорости. ([TinyGo][2])

Но для AutoTrace у обычного Go есть большое преимущество:

```text
Native build
     │
     ├── exact same packages
     └── WASM build
```

Никакой отдельной TinyGo-совместимости.

У вас будут использоваться:

* generics;
* heaps;
* hash maps;
* spatial indices;
* graph algorithms;
* possibly goroutines;
* сложные allocator patterns;
* profiling;
* property-based tests.

Сначала стоит добиться:

```text
native Go == wasm Go
```

по результату.

После этого сделать benchmark:

```text
Go WASM
vs
TinyGo WASM
```

и только если TinyGo реально выигрывает, добавить его как дополнительный target.

Не стоит строить архитектуру вокруг размера `.wasm` раньше, чем вокруг корректности алгоритма.

---

# 4. Критически важно: WASM запускать не в UI thread

Вот так делать нельзя:

```text
Obsidian UI
     ↓
layout()
     ↓
500 ms freeze
```

Нужно:

```text
Main UI thread
       │
       │ transferable ArrayBuffer
       ▼
Web Worker
       │
       ▼
autotrace.wasm
       │
       ▼
Go Engine
       │
       ▼
ScenePatch
       │
       ▼
Main UI thread
```

И для сайта, и для Obsidian должен использоваться практически один и тот же worker package.

Например:

```text
packages/
    autotrace-client/
    autotrace-worker/
    autotrace-renderer/
```

---

# 5. Это особенно хорошо подходит Obsidian

У Obsidian есть важное ограничение: Node.js и Electron API официально доступны только на desktop; если плагин от них зависит, он должен быть помечен `isDesktopOnly`. ([Developer Documentation][3])

Поэтому архитектура:

```text
Obsidian
→ Web API
→ Worker
→ WASM
```

значительно лучше архитектуры:

```text
Obsidian
→ Node child_process
→ native Go executable
```

Первая потенциально позволяет сохранить:

```text
Desktop
+
Mobile
```

в рамках одной архитектуры.

---

# 6. Но native Go всё равно нужен

Получается очень полезная двухуровневая система.

| Среда                    | Исполнение                |
| ------------------------ | ------------------------- |
| Website                  | Go WASM                   |
| Obsidian desktop         | Go WASM                   |
| Obsidian mobile          | Go WASM                   |
| Server                   | Native Go                 |
| CLI                      | Native Go                 |
| benchmarks               | Native Go                 |
| batch processing         | Native Go                 |
| extremely large diagrams | Native Go/server optional |

То есть **WASM — способ доставки ядра в клиент**, а не отдельная реализация ядра.

# 7. ABI нужно сделать очень узким

Это существенно влияет на производительность.

Плохой API:

```text
getBlock()
getPort()
setX()
setY()
getEdge()
getSegment()
...
```

Если JavaScript ↔ WASM вызываются десятки тысяч раз, boundary overhead начнёт съедать выигрыш Go.

Лучше иметь буквально несколько coarse-grained операций:

```text
engine_create()
engine_load()
engine_layout()
engine_apply()
engine_query()
engine_free()
```

По смыслу:

```text
binary Model
      ↓
    WASM
      ↓
binary Scene
```

а не:

```text
JS object
↓
WASM call
↓
JS object
↓
WASM call
↓
...
```

# 8. Я бы вообще не использовал JSON внутри hot path

JSON оставить для:

```text
files
debug
REST API
human-readable interchange
```

Но внутри:

```text
TS Worker ↔ WASM
```

лучше передавать бинарное представление.

Для вашего проекта я бы рассматривал:

```text
FlatBuffers
```

как основной кандидат.

Причина — у вас очень много повторяющихся геометрических данных:

```text
10 000 points
5 000 segments
1 000 blocks
5 000 ports
labels
metrics
```

Scene может выглядеть условно так:

```text
Scene
├─ float32 blockX[]
├─ float32 blockY[]
├─ float32 blockW[]
├─ float32 blockH[]
├─ uint32 edgeStart[]
├─ uint32 edgeCount[]
├─ float32 pointsXY[]
├─ uint32 portBlock[]
├─ float32 portXY[]
└─ ...
```

Для таких данных бинарная SoA-модель намного эффективнее дерева JS-объектов.

# 9. Для hot geometry предпочтительнее SoA

Не:

```go
type Point struct {
    X float64
    Y float64
}

[]Point
```

во всех критических алгоритмах.

Для крупных плотных массивов можно использовать:

```go
type Points struct {
    X []float32
    Y []float32
}
```

или packed arrays.

Это потенциально улучшает:

```text
cache locality
sequential access
serialization
WASM memory transfer
```

Но применять SoA стоит там, где benchmarks показывают смысл.

# 10. Внутри ядра лучше избегать интерфейсов в hot path

Например routing loop:

```go
interface {
    Cost(...)
}
```

вызываемый миллионы раз, может оказаться неоптимальным.

В критических местах лучше:

```go
struct
+
concrete functions
+
generics where useful
```

А интерфейсы оставить на архитектурных границах.

# 11. Сразу заложить arenas / scratch buffers

AutoTrace идеально подходит для reuse памяти.

Например A* сейчас может на каждом edge создавать:

```text
map
heap
visited
neighbors
path
```

Лучше:

```go
type RoutingScratch struct {
    Heap       []Node
    GScore     []float32
    Parent     []uint32
    Generation []uint32
}
```

и переиспользовать память.

То есть:

```text
route edge #1
      ↓
reuse buffers

route edge #2
      ↓
reuse buffers

route edge #5000
```

а не тысячи раз нагружать GC.

---

# 12. Для routing grid можно вообще убрать map

Например вместо:

```go
map[Point]Node
```

использовать:

```text
index = y * gridWidth + x
```

и массивы:

```go
gScore[index]
parent[index]
flags[index]
```

Это даст гораздо больший выигрыш, чем выбор Go против Rust или Go против TinyGo.

Для направления:

```text
state =
cellIndex * 4
+
direction
```

И A* state становится обычным integer.

---

# 13. Generation counters вместо очистки массивов

Очень полезная техника для большого количества A*.

Вместо:

```go
clear(visited)
```

после каждой трассы:

```go
generation++
```

и:

```go
if visitedGeneration[i] != generation {
    // logically empty
}
```

Это позволяет избежать:

[
O(W\times H)
]

очистки grid на каждом edge.

# 14. Spatial index тоже должен находиться в Go

Не:

```text

↓
JS spatial index
↓
Go routing
```

а:

```text

├── block spatial hash
├── segment spatial hash
├── label index
└── routing occupancy
```

Иначе вы постоянно пересекаете WASM boundary.

# 17. Я бы не делал SVG единственным renderer

Для небольших схем SVG великолепен:

```text
< 100–300 blocks
```

потому что:

* удобно выделять элементы;
* DOM events;
* CSS;
* text;
* accessibility.

Но на тысячах объектов DOM становится существенным bottleneck.

Поэтому архитектуру лучше сразу сделать:

```text
Scene
 ├─ SVG renderer
 └─ Canvas/WebGL renderer
```

Я бы ориентировался на:

```text

→ compatibility/debug/small diagrams

Canvas2D
→ основной editor

WebGL
→ very large diagrams
```

# 18. Interaction layer не должен проходить через Go для каждого mousemove

Например drag:

```text
mousemove
mousemove
mousemove
mousemove
```

не должен каждый раз запускать полный Go layout.

Нужно:

```text
TS interaction
      ↓
temporary visual transform
      ↓
pointerup
      ↓
Mutation
      ↓
Go optimizer
      ↓
ScenePatch
```

При необходимости можно делать throttled preview:

```text

```

но не synchronous call на каждый browser event.

# 19. ScenePatch важнее, чем кажется

После перемещения одного блока не нужно возвращать всю Scene на несколько мегабайт.

Например:

```text
MoveBlock #145
```

Go определяет:

```text
dirty blocks: 145, 148
dirty ports: 12
dirty edges: 31
dirty labels: 8
```

и возвращает:

```text
ScenePatch
```

а не полный Scene.

Пример:

```text
ScenePatch {
    changedBlocks[]
    changedPorts[]
    changedEdges[]
    changedLabels[]
    removed[]
}
```

Это особенно важно для Obsidian mobile.

# 20. Очень полезна revision-модель

Каждая Scene:

```text
revision = 105
```

Mutation:

```text
baseRevision = 105
```

Result:

```text
revision = 106
```

Если UI получает старый результат Worker:

```text
revision 103
```

он просто отбрасывается.

Это защищает от race condition при быстром editing.

# 23. И ещё одно важное решение: Go Core должен быть stateful

Я бы не ограничивал API функцией:

```go
Layout(model)
```

Нужен объект:

```go
engine := NewEngine(model)
```

который хранит:

```text
graph indexes
spatial indexes
routing grid
route occupancy
scratch buffers
previous solution
dirty regions
```

Тогда:

```go
engine.Apply(MoveBlock{...})
```

не пересчитывает всё.

Для интерактивного редактора это даст огромный выигрыш.

Архитектурно:

```text
Load
 ↓
Engine State
 ↓
Mutation #1
 ↓
incremental update
 ↓
Mutation #2
 ↓
incremental update
```

## Что получится в итоге

Самая удачная архитектура для AutoTrace будет выглядеть примерно так:

```text
             AUTOTRACE PLATFORM

              Go Algorithm Core
                     │
       ┌─────────────┴─────────────┐
       │                           │
   Native Go                     WASM
       │                           │
 ┌─────┼──────┐             ┌──────┴───────┐
 │     │      │             │              │
CLI  Server Benchmark    Web Worker   Obsidian Worker
                            │              │
                            └──────┬───────┘
                                   │
                            TypeScript API
                                   │
                              ScenePatch
                                   │
                    ┌──────────────┼──────────────┐
                    │              │              │
                   SVG          Canvas2D        WebGL
```

Именно **Go → WASM → Worker → ScenePatch → TS renderer** я считаю оптимальной базовой архитектурой.

Это также хорошо согласуется с актуальным Go: официальный toolchain поддерживает WebAssembly, экспорт функций через `go:wasmexport` появился с Go 1.24, а Node может исполнять `js/wasm`; при этом Obsidian прямо предупреждает, что Node/Electron-зависимости делают плагин desktop-only. ([Go][4])

Для **максимальной производительности** я бы дополнительно сделал одну вещь: спроектировал ядро не просто как Go-библиотеку, а как **инкрементальный retained-mode geometry engine** с persistent spatial indexes, reusable routing arenas и dirty-region recomputation. Для AutoTrace это потенциально важнее любых процентов разницы между Go WASM и TinyGo WASM: перемещение одного блока сможет приводить к перерасчёту условно 20–50 рёбер вместо всего графа из 5000 соединений.
